# API キーと記録投入（api-keys / records）

## 目的

ログインの Cookie を持てない相手（ボタン 1 つのデバイス、外部のサービスや自動化）から、LifeHub に記録を入れられるようにする。記録を入れる入口は **1 つのエンドポイント（`POST /api/records`）** にまとめ、何の記録かを本文の `type` で選ぶ。入口を記録の種類ごとに作らないのは、デバイス側の作り（キー 1 本・URL 1 つ）を記録の種類で変えずに済ませるため。

使っている例: レモンの木の世話を記録するボタン（[`iot/lemon-record-button/`](../../iot/lemon-record-button/README.md)）。

## 画面

設定（`/settings`）の「外部連携」に、カレンダーの配信 URL（[calendar-feeds.md](calendar-feeds.md)）と MCP クライアント（[mcp-clients.md](mcp-clients.md)）と並べて置く（`src/features/api-keys/components/ApiKeyList.tsx`）。外の仕組みに渡したアクセスを 1 か所にまとめる。

- 発行したキーが一覧に並ぶ。行は名前と「最後に使われた日時」（まだなら「まだ一度も使われていません」）で、右に失効のボタン。
- 「API キーを発行」で名前を決めると 1 本増え、**キーはそのとき 1 度だけコピーできる**（[architecture.md](../architecture.md#書き込み) の秘密の発行）。サーバーはキーのハッシュしか持たないので、閉じたら二度と出せない。なくしたら発行し直して古いほうを失効させる。
- 名前は渡した先を見分けるためだけのもの（「レモンのボタン」など）。変更はできない（変えたいほど使い分けるなら、発行し直せば済む）。
- 失効は確認してから消す（そのキーを持つデバイスは記録できなくなる）。
- 一覧に出るのはログイン中のユーザーが発行したキーだけ。キーで入れた記録は、記録した人が不明になる（キーの持ち主にはしない）。キーを持つボタンは家の誰が押しても同じキーで送るので、持ち主を記録者にすると誤りになるため。代わりにそのキーの名前を記録に残し、ホームのタイムラインで記録した人の代わりに出す（[lemon.md](lemon.md)）。

## 記録投入のエンドポイント

`POST /api/records`、`Authorization: Bearer <API キー>`、本文は JSON。

```json
{ "type": "lemon", "careTypes": ["mist", "water"] }
```

| `type` | 項目 | 作られる記録 |
|---|---|---|
| `lemon` | `careTypes`（必須）, `note`, `doneAt`, `id` | レモンの世話の記録（[lemon.md](lemon.md)）。項目と規則は画面から記録するときと同じ |

- `doneAt`（ISO 8601）は省略すると**受け取った時刻**になる。時計を持たない（持っても合わせる手間をかけたくない）デバイスは、今起きたことを送るだけで済む。
- `id`（UUID）は省略できる。送る側が決めておけば、届いたか分からずに送り直しても二重に作られない（同じ id の作成の扱いは [architecture.md](../architecture.md#オフラインの書き込み)）。
- 応答は 201 と、作った記録（その機能の service が作成で返すもの）。キーが無い・知らない・失効したキーは 401、本文が規則に合わなければ 400（`{ message }`）。
- 入力スキーマは `shared/validation/records.ts` の `recordSchema`（`type` で分ける discriminated union）。受け付けは `server/features/records/service.ts` が `type` で振り分けて各機能の service に渡すだけで、記録の規則は各機能が持つ。記録の種類を増やすときは、この 2 か所に 1 つずつ足す。
- ログインを確かめない Hono の口（`server/app.ts`）で、キーの照合は Hono の `bearerAuth` に任せる。

## キー

- 作り方はカレンダーの配信 URL のトークンと同じ（[calendar-feeds.md](calendar-feeds.md#トークン)）。
- **SHA-256 のハッシュだけを保存する**（`api_keys.key_hash`。`server/lib/secret.ts` の `hashSecret`）。DB を読めても書き込みの資格までは渡さないため。配信 URL のトークンも同じ関数でハッシュにする。遅いハッシュ（bcrypt など）や塩を使わないのは、256 ビットの乱数は総当たりもレインボーテーブルも成り立たず、遅くしても守れるものが無いため。遅いハッシュは塩を伴うので、受け取ったキーからハッシュを作って DB を引くこともできなくなる。人が決めた値や短い値をキーにするなら、この前提は崩れる。
- 照合はハッシュの一致を DB に引かせる。照合と最終使用日時（`last_used_at`）の記録は 1 文（`UPDATE ... RETURNING`）にまとめ、受け付け 1 回の往復を増やさない。
- WHY NOT better-auth の API キーのプラグイン: 使い回しの上限・補充・権限・メタデータなどの列を持つ大きなテーブルを Drizzle のスキーマに書き写して版ごとに追うことになる一方、ここで要るのは「ハッシュを引いて持ち主を返す」だけで、自前でも数行で済む。

## データ

`api_keys`（[data-model.md](../data-model.md)）。キーで入れた記録の記録者の扱いは各機能のデータ（[lemon.md](lemon.md#データ)）。

## API（キーの管理）

| 手続き | 種類 | 認証 | 内容 |
|---|---|---|---|
| `apiKeys.list` | 読み出し | セッション | 自分が発行したキーの一覧（id, name, createdAt, lastUsedAt）。キーそのものは含まない |
| `apiKeys.create` | 書き込み | セッション | 発行（名前を送る）。一覧の 1 行（`item`）とキー（`secret`）を返す。キーを受け取れるのはこの応答だけ |
| `apiKeys.revoke` | 書き込み | セッション | 失効（入力は `id`。自分のものだけ） |

| メソッド | パス | 認証 | 内容 |
|---|---|---|---|
| POST | `/api/records` | **API キー** | 記録の投入（上記） |

入力スキーマは `shared/validation/api-keys.ts`。

## MCP ツール

無し。AI ツールには MCP があり、API キーを発行できる必要は無い（秘密を増やす経路を増やさない）。
